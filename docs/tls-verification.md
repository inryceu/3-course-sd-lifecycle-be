# TLS verification: BoardSync production-like profile

**Date:** 2026-11-24. **Stack:** `docker-compose.prod.yml` (postgres, backend, nginx) started with `up -d --build --wait` on an empty database volume, a self-signed certificate from `nginx/generate-self-signed-cert.sh`, host ports 18080 (HTTP) and 18443 (HTTPS) through `HTTP_PORT` / `HTTPS_PORT`. Client: OpenSSL 3.2.2 and curl on Windows (Git Bash), Docker Desktop. The commands below use the default ports 80/443; the run used the ports above.

Everything in this file was run in that session. Nothing is recorded as verified that was not run; what was not run is listed at the end.

## 1. Certificate and stack startup

```bash
./nginx/generate-self-signed-cert.sh     # creates ssl/ itself; works in Git Bash
docker compose -f docker-compose.prod.yml up -d --build --wait
```

Result: `ssl/boardsync.crt` (CN `boardsync.local`, SAN `localhost`, `127.0.0.1`) and `ssl/boardsync.key` created from a checkout without an `ssl/` directory; all three containers reported `Healthy`; the backend log showed `Applied 7 migration(s)` before the first request, and `POST /api/v1/auth/register` (201) and `POST /api/v1/auth/login` (200) worked on the fresh volume.

## 2. Protocol matrix

```bash
echo | openssl s_client -connect localhost:443 -tls1   -cipher 'DEFAULT:@SECLEVEL=0'
echo | openssl s_client -connect localhost:443 -tls1_1 -cipher 'DEFAULT:@SECLEVEL=0'
echo | openssl s_client -connect localhost:443 -tls1_2
echo | openssl s_client -connect localhost:443 -tls1_3
```

`@SECLEVEL=0` is needed on a modern OpenSSL so that the client does not refuse TLS 1.0/1.1 itself; without it the refusal would come from the client, not from nginx.

| Protocol | Result |
|----------|--------|
| TLS 1.0 | refused by the server: `tlsv1 alert protocol version`, alert number 70 |
| TLS 1.1 | refused by the server: `tlsv1 alert protocol version`, alert number 70 |
| TLS 1.2 | handshake completes, `Protocol: TLSv1.2`, cipher `ECDHE-RSA-AES256-GCM-SHA384` |
| TLS 1.3 | handshake completes, `Protocol: TLSv1.3`, cipher `TLS_AES_256_GCM_SHA384` |

## 3. HTTP to HTTPS redirect

```bash
curl -I http://localhost/api/v1/health/alive
```

Result: `HTTP/1.1 301 Moved Permanently`. The `Location` header was not captured in this run; the configuration is `return 301 https://$host$request_uri;`, which drops a non-default port (irrelevant on 80/443). No HSTS header is sent on the plaintext response.

## 4. Security headers, one HSTS

```bash
curl -kI https://localhost/api/v1/health/alive
curl -kI https://localhost/nonexistent          # a 404 from the backend
```

Result: both responses carry exactly one `Strict-Transport-Security: max-age=31536000; includeSubDomains` (counted with `grep -ic`), plus `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and the default `Content-Security-Policy`. HSTS and the other security headers come from the backend's helmet; nginx adds none, so none is duplicated. Responses generated by nginx itself (for example 413, 502) carry none of them.

## 5. Forwarded client address and scheme

A throwaway echo server replaced the backend behind a second nginx container using the same configuration files, and printed the headers it received.

| Request | Backend saw |
|---------|-------------|
| plain `GET /api/v1/x` | `Host: localhost`, `X-Real-IP` and `X-Forwarded-For` = client address (`192.168.144.1`, the Docker gateway for a host client), `X-Forwarded-Proto: https`, `X-Forwarded-Port: 443` |
| same with client headers `X-Forwarded-For: 9.9.9.9` and `X-Forwarded-Proto: http` | the same values as above; the forged ones are discarded |
| `/socket.io/` and `/` with `Connection: Upgrade`, `Upgrade: websocket` | the same forwarded headers, `Connection: upgrade`, `Upgrade: websocket` |
| plain request without `Upgrade` | no `Connection` and no `Upgrade` header |

Rate limiting through the real stack (`TRUST_PROXY=1`, login limit 10 per window):

- One host client sent 15 logins, each with a different forged `X-Forwarded-For`: nine `401` (one login had already been counted), then six `429`. The forged header did not change the key.
- A second client (a container on the compose network, another source address) then got `401 401 401`: its own bucket.
- The host client's next login was still `429`.

## 6. REST over HTTPS and Socket.IO over `wss://`

```bash
curl -k https://localhost/api/v1/health/alive    # 200 {"status":"ok","timestamp":...,"uptime":...}  (no "database" field)
curl -k https://localhost/api/v1/health/ready    # 200 {"status":"ok","database":"up",...}
```

A `socket.io-client` script (self-signed certificate accepted with `rejectUnauthorized: false`), authenticated with a freshly registered user's token, connected to `wss://localhost/realtime` with `transports: ['websocket']` and with `['polling','websocket']`; both ended connected on the `websocket` transport.

## 7. Liveness, readiness and the container healthchecks with Postgres stopped

`docker compose stop postgres`, 45 s later:

| Probe | Result |
|-------|--------|
| `GET /api/v1/health/alive` | `200`, no `database` field |
| `GET /api/v1/health/ready` | `503 {"status":"error","database":"down",...}` |
| `backend` container | `unhealthy` (readiness) |
| `nginx` container | `healthy` (liveness) |

After `docker compose start postgres` and 40 s: readiness `200`, all three containers `healthy`.
